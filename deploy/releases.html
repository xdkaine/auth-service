Auth service releases

Standalone source and container builds for the AD-backed OIDC provider and Auth Manager. The repository supplies standalone image builds. Production deployment and application-access configuration are documented in application-access.html.

Build and verify

docker build --target builder -t auth-service:builder .
docker run --rm --network none auth-service:builder npm run lint
docker run --rm --network none auth-service:builder npm test
docker build --target runner -t auth-service:runtime .
docker build --target migration-tool -t auth-service:migrate .

Node 22 is the container build environment. The runner uses a non-root account, retains compiled code and runtime dependencies, and checks final packaging during its build. It never runs migrations on startup. The separate migration-tool image retains the Prisma CLI and migration history. CI checks pull requests to dev/main, validates pushes, and publishes immutable SHA-tagged runtime and migration images only after checks pass. It does not apply Kubernetes manifests.

Database boundary

This is a source and image separation, not a standalone database migration. The development service still shares the portal database. Production Auth runs in its own database and namespace, with no Portal runtime or production Portal database connection. Its initial bootstrap preserves the same coordinated schema history, including unused Portal tables. The portal owns the AuditLog table, and the auth migration 20260827000000_identity_console_product alters that table. A fresh empty database is therefore not supported by this auth history alone. Preserve the existing portal-first, auth-second migration coordinator, advisory lock, schema-owner role, and runtime grant verification. The existing coordinated release must consume this repository's tested migration image digest before a service rollout. Do not run independent concurrent migration jobs from the two repositories.

All extracted SQL migration files are preserved byte for byte. Do not rewrite their history or use db push/reset. Keep the auth runtime database role separate from the portal runtime and migration roles. A future database split needs an explicit audit ownership and data migration design.

Environment contract

Supply DATABASE_URL, Redis connectivity, AUTH_ISSUER, persistent AUTH_JWKS, AUTH_COOKIE_KEYS, OIDC client configuration, directory connection/bind settings, and encryption keys through your environment's secret manager. See src/config.ts and src/client-secret-encryption.ts for exact validation. Preserve the existing issuer, signing keys, cookie keys, encryption keys, registered redirect URIs, and Redis data when changing image ownership. Use distinct development and production secrets, OIDC registrations, namespaces, and persistence. Configure LDAPS and database certificate trust. No live credentials, private keys, server addresses, or production data are included here.

Promotion and recovery

Review dev into main, run the same checks, record immutable image digests, and approve the production rollout independently. Do not point production at mutable dev tags. Retain the previous image digest and data backup before schema changes; use forward-compatible migrations and code rollback without deleting database evidence. Protect main with required reviews and CI checks in repository settings.
