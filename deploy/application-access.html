Restricted application access

In Auth Manager, open Applications, select the registered Headlamp application, and enable restricted access. Only an AD-authenticated Auth Manager administrator can change this policy; local recovery accounts can view it.

  1. Create your group in Active Directory and add the intended users as direct members.
  2. Copy its complete distinguished name, such as CN=Cluster Viewers,OU=Groups,DC=example,DC=org.
  3. Add a mapping in the application's access policy, select viewer or administrator, and save.
  4. Start a new Headlamp sign-in to obtain a token with the current mapped access.

A restricted application with no mappings denies everyone. Successful AD sign-in alone does not grant application access. Direct group membership is checked with a fresh service bind. Nested and primary-group membership are not expanded. Use the complete DN; matching only a common name would confuse groups in different directory containers.

Enforcement

The server checks the current database policy and live AD membership before completing login or consent, before issuing authorization codes for existing sessions, and again at token claims issuance. Disabled accounts, locked accounts, unavailable dependencies, invalid policies and unmatched memberships deny access. Unrestricted applications receive no mapped Kubernetes claims. Bootstrap clients are explicitly exempt and must not be used as the Kubernetes audience.

Tokens carry the application-specific k3s_groups claim. Kubernetes must trust the exact Headlamp client audience and require an approved mapped group, then bind the issuer-prefixed groups to the two fixed roles. Auth Manager controls membership mappings; it does not receive Kubernetes administrative credentials.

Expiration and recovery

Already-issued ID tokens remain valid until their existing ten-minute expiry. Removing a mapping or group membership prevents new tokens; it does not instantly revoke an offline token. Existing token/service-account recovery access is independent of this application policy. Denials and policy mutations are audited without recording directory membership lists.

Database rollout

Apply the additive 20260906050000_restricted_application_access migration before starting the new image. Existing clients default to unrestricted, preserving existing behavior; explicitly set Headlamp to restricted with an empty mapping list during deployment. This adds one JSONB column to OidcClient and creates no new table or role grants. The service still uses the coordinated schema history described in releases.html. Preserve the new column on rollback; old code does not enforce it, so Kubernetes must continue requiring mapped groups until the restriction-aware image is restored.
