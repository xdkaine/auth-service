Server-enforced session termination

Clearing a cookie is insufficient. Applications must check the provider session before accepting a retained credential. Application logout ends the backing SSO session before clearing local state; applications sharing that SSO session lose access together. Independent device sessions remain separate.

Application integration

Authenticate server-to-server with the registered application's current client ID and secret using HTTP Basic over HTTPS. POST form fields sid and sub to /session/status. Require HTTP 200 and {"active":true} on every protected request, with no positive cache. The SID must come from a verified ID token. Missing, expired, unknown, foreign-client and revoked sessions deny; dependency failures must also deny.

For logout, POST sid to /session/backchannel-logout with the same client credentials. HTTP 200 contains a boolean destroyed; false means the session is already absent. Do not report successful server logout on an error. Preserve retry state when termination is unavailable. This replaces the prior 204 success response; callers should accept successful 2xx responses.

Redis session deletion atomically leaves a revocation marker for the maximum session lifetime. Concurrent stale writes cannot restore the deleted session. Interactive access and refresh tokens remain bound to their provider session. Auth Manager console logout also requires successful server-record deletion before clearing its cookie.

Kubernetes

An offline JWT authenticator cannot enforce live revocation. A dedicated /session/kubernetes-token-review endpoint verifies signed AD-authenticated claims, exact configured audience, required K3s access/role claims and live session state. Configure KUBERNETES_OIDC_CLIENT_ID and a random KUBERNETES_WEBHOOK_SECRET of at least 32 characters. The API server authenticates with that bearer secret over verified HTTPS; never expose it to browsers.

Replace the equivalent offline JWT authenticator, rather than adding an alternative that could bypass revocation. Preserve existing API audiences and include the configured client audience. Set the webhook cache TTL to zero. Kubernetes still has an outer successful-authentication cache: the deployed version retains results for approximately ten seconds. Already-open direct Kubernetes streams require separate connection management.

The deployment's patched Headlamp validates live sessions before requests and monitors long-lived connections. Enable HEADLAMP_REQUIRE_SESSION_REVOCATION=true with its selected cluster. Application request cancellation does not undo a previously accepted infrastructure operation.

Recovery

If Auth or Redis is unavailable, protected application requests fail closed and logout reports an error. Maintain separate operator credentials for cluster recovery. Kubernetes service-account credentials have their own revocation mechanism; an Auth logout cannot revoke them. No schema migration is required for this release.

Deployment scripts that generate the webhook credential are one-shot operations. Do not rerun them against an active webhook: restore or rotate the Auth secret and API-server webhook credential as a matched pair. Keep private pre-change manifests and an independent operator kubeconfig available. Restoring the former offline authenticator also restores its token-until-expiry limitation; it is an availability recovery choice, not equivalent session enforcement.
